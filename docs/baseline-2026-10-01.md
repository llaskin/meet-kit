## Files changed outside Task 4's explicit list

Task 4's file list is `src/core/{calendar-store,busy,booking-core,cancel-booking}.js` plus the `calendar-store`/`cancel-booking`/`cancellation-store` tests. One more file needed a fix: `tests/helpers/d1.js`.

Porting `'two concurrent cancels of one booking do not blow up'` (from `cancellation-store.test.js`) surfaced a real bug in the shared `realDB().batch()` helper (written in Task 0–3, used by every `realDB()` consumer): its per-statement loop did `for (const s of stmts) out.push(await s.run())`, which yields to the microtask queue *between* `BEGIN` and `COMMIT`. Two concurrent `cancelPublicBooking()` calls against the one shared synchronous `DatabaseSync` connection could then interleave: the second call's `BEGIN` landing while the first transaction was still open throws `"cannot start a transaction within a transaction"`, turning one of the two concurrent promises into a rejection instead of a fulfillment. The source repo's original inline test fixture never had this bug because its `batch()` ran its statement loop with no internal `await` at all.

Fixed by removing the only yield point inside the transaction — the statements now execute synchronously in a `.map()`, matching the original fixture's contract (the helper's own header already claimed to "mirror the adapter the source tests defined inline"):

```js
async batch(stmts) {
  db.exec('BEGIN')
  try {
    const out = stmts.map((s) => {
      const r = db.prepare(s.sql).run(...s.args)
      return { success: true, meta: { changes: Number(r.changes) } }
    })
    db.exec('COMMIT')
    return out
  } catch (e) { db.exec('ROLLBACK'); throw e }
}
```

(Also added `sql` as a property on the object `wrap()` returns: the new `batch()` reads each statement's text straight off the statement object — `db.prepare(s.sql).run(...s.args)` — rather than calling the statement's own `.run()` method, which still closes over `sql` via the `wrap(sql)` closure and works fine on its own but doesn't give `batch()` anything to read without it.)

Verified this is a strict tightening, not a behavior change for anyone else: before the fix, the full suite was 127/128 (only the one concurrent-cancels test failing); after the fix, 128/128, with every other `realDB()` consumer (`public-bookings-store`, `rate-limit`, `scaffold`, `schema`) staying green in both runs.
